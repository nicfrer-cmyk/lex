## 1. ארכיטקטורה

### הגבול המרכזי

```
┌──────────────────────────────────────────────┐
│  CRM  —  Netlify + Supabase                  │
│                                              │
│  מרכז שיחות (src/call-center.js)             │
│  שער הכלים   (voice-gateway Edge Function)   │
│  מנוע השיחה  (_shared/voice/orchestrator.ts) │
│  הנתונים     (app_data + call_*)             │
└────────────────────┬─────────────────────────┘
                     │  HTTPS + HMAC-SHA256
                     │
┌────────────────────┴─────────────────────────┐
│  Voice Gateway  —  שרת Linux פרטי            │
│                                              │
│  Orchestrator (Python)  ←→  Asterisk 22      │

```

### הכלל שמסביר את כל שאר המסמך

**כל היגיון השיחה חי ב-CRM.** מי המתקשר, מה מותר לסוכן לעשות, מה נחשב
דחוף, מה נכתב לתיק — הכול שם. שרת הקול עושה דבר אחד: מביא קול מקו טלפון
אל המנוע הזה, ומחזיר קול בחזרה.

זו הסיבה שמצב הבדיקה אמין. שיחת סימולציה מהדפדפן ושיחת טלפון אמיתית
נכנסות **לאותן שלוש פונקציות**:

| | שיחה אמיתית | שיחת סימולציה |
|---|---|---|
| מקור הטקסט | STT | תיבת קלט |
| מנוע | `orchestrator.ts` | `orchestrator.ts` |
| כלים | `voice/tools.ts` | `voice/tools.ts` |
| הרשאות | `agent_tools` | `agent_tools` |
| כתיבה ל-CRM | `saveOfficeDb` | `saveOfficeDb` |

ההבדל היחיד הוא `is_simulation=true` על השורה, כדי שאפשר יהיה לסנן.

### הממצא שעיצב את הסכמה

ב-LexTrack **אין טבלאות** `clients` / `cases` / `tasks`. כל ה-CRM הוא ערך
`jsonb` יחיד ב-`app_data.data`, שורה אחת לכל משרד, ומזהי הישויות בתוכו הם
מחרוזות base36 שנוצרו ע"י `uid()` ב-`app.js`.

לכן `client_id` / `lead_id` / `matter_id` בטבלאות מרכז השיחות הם **`text`
ללא foreign key**. FK לטבלה שאינה קיימת אינו ניתן לכתיבה, ו-`uuid` לא
תואם לפורמט. אותה החלטה בדיוק כבר קיימת ב-`20260804000000_ai_center.sql`.

כתיבה ל-blob היא read-modify-write על שורה שלמה, ולכן היא נעשית **רק**
דרך `saveOfficeDb`, שמבצע בדיקה אופטימית: אם המשתמש שמר בדפדפן בינתיים,
הכתיבה נדחית במקום לדרוס בשקט את מה שהוא הרגע הקליד.

## 2. מסד הנתונים

שתי מיגרציות, שתיהן additive. אף טבלה קיימת לא משתנה, אף עמודה לא נמחקת,
אין פעולה הרסנית, וכל אובייקט נוצר עם `if not exists` — כך שהרצה חוזרת
בטוחה.

| טבלה | תפקיד |
|---|---|
| `phone_lines` | קווי הטלפון. `provider_status` ו-`sip_status` נפרדים בכוונה |
| `voice_agents` | הסוכנים. סוכן = שורה, לא קוד |
| `agent_tools` | **גבול הסמכות.** כלי שאינו כאן — נחסם ונרשם |
| `call_sessions` | שיחה. `unique(office_id, external_call_id)` |
| `call_transcript_segments` | תמלול בקטעים. `unique(call_id, sequence)` |
| `call_events` | ציר הזמן |
| `call_actions` | כל פעולה, כולל שנחסמה. `unique(call_id, idempotency_key)` |
| `call_center_settings` | הגדרות, שמירת נתונים, עצירת חירום |
| `voice_gateway_status` | heartbeat |
| `voice_request_nonces` | Replay protection |
| `voice_rate_limits` | מגבלת קצב |

### שלוש החלטות שכדאי להכיר

**`call_events.occurred_at` ולא `timestamp`.** `timestamp` הוא
`col_name_keyword` ב-Postgres; `select timestamp from …` הוא ביטוי
דו-משמעי שהמנתח עלול לפרש כתחילת literal. שם חד-משמעי עדיף בעמודה
שנקראת בכל שאילתה של ציר הזמן.

**אין דגל `online` ל-heartbeat.** המצב נגזר מ-`last_heartbeat_at` דרך
`voice_gateway_state()`. שרת שנפל באמצע לא יספיק לכתוב "offline", והמסך
היה נשאר ירוק בזמן שאף שיחה לא נענית.

**אין מדיניות `insert`/`update` על טבלאות השיחה.** ראה §3.

### אידמפוטנטיות

שלושה אילוצים ברמת הסכמה, כי הגנה בקוד לבדה נשברת ב-retry מקבילי:

```sql
unique (office_id, external_call_id)   -- שיחה לא נפתחת פעמיים
unique (call_id, sequence)             -- קטע תמלול לא מוכפל
unique (call_id, idempotency_key)      -- פעולה לא מבוצעת פעמיים
```

מפתח הפעולה נגזר מהכלי ומהקלט המנורמל (`canonicalize` ב-`gateway.ts`),
ולכן `{a:1,b:2}` ו-`{b:2,a:1}` נותנים את אותו מפתח. זה מה שמונע פגישה
שנייה כשהמודל חוזר על עצמו או כששרת הקול שידר מחדש אחרי timeout.

## 3. אבטחה

### שכבה 1 — טבלאות השיחה אינן ניתנות לכתיבה מהדפדפן

לטבלאות `call_sessions`, `call_transcript_segments`, `call_events`,
`call_actions` יש **רק** מדיניות `select`. אין `insert`, אין `update`, אין
`delete`.

הסיבה קונקרטית: בלי זה, דפדפן יכול להצהיר "התקבלה שיחה מלקוח X שביקש את
פרטי התיק" — ומכאן נוצרים לידים, משימות ופגישות אמיתיים. כל כתיבה עוברת
דרך Edge Function עם `service_role`, שמאמתת חתימה או JWT.

הבדיקה `טבלאות השיחה אינן ניתנות לכתיבה מהדפדפן` ב-`test/call-center.test.js`
מנתחת את קובץ המיגרציה ונופלת אם מישהו יוסיף מדיניות כתיבה בעתיד.

### שכבה 2 — HMAC + Replay

כל בקשה משרת הקול נושאת:

```
X-Voice-Office     מזהה המשרד
X-Voice-Timestamp  שניות Unix
X-Voice-Nonce      מזהה חד-פעמי
X-Voice-Signature  HMAC-SHA256 של `${timestamp}.${nonce}.${body}`
```

שלוש הגנות, וכל אחת סוגרת פרצה שהאחרות משאירות:

1. **חתימה** — מוכיחה החזקה בסוד. הגוף חתום, ולכן אי אפשר לקחת בקשה
   לגיטימית ולשנות בה את מספר המתקשר.
2. **חלון 5 דקות** — מצמצם שידור חוזר, **לא סוגר אותו**.
3. **nonce** — מפתח ראשי ב-`voice_request_nonces`. שידור חוזר נכשל
   ב-`insert`. זו ההגנה שבאמת עוצרת replay.

בלי `VOICE_GATEWAY_SECRET` כל בקשה נדחית ב-503. endpoint טלפוניה פומבי
בלי אימות גרוע מהיעדר טלפוניה.

הבדיקה `חתימת Python מתקבלת ע"י המאמת של ה-CRM` מוודאת התאמה בין שתי
השפות, כולל גוף בעברית — חוסר התאמה בקידוד היה הופך כל בקשה ל-401 ונראה
כמו "השרת לא עונה".

### שכבה 3 — ה-AI לעולם לא מקבל SQL

הסוכן מבקש כלי **בשם** עם קלט מובנה. `execVoiceTool` בודק, לפי הסדר:

1. הכלי קיים בקוד?
2. רשום ב-`agent_tools` לסוכן הזה?
3. `enabled`? `available`?
4. עצירת חירום פעילה?
5. הקלט עובר סכימה שדוחה שדות לא מוכרים?

רק אז מבוצע. כל דחייה נרשמת כשורת `blocked` ב-`call_actions` — שורה כזו
היא ראיה שהמנגנון עבד, והיא מה שמאפשר לענות על "מה הסוכן ניסה לעשות ולא
הורשה".

`additionalProperties: false` בסכימה אינו היגיינה: הקלט מגיע ממודל
שמאזין למתקשר, לא ממפתח.

### שכבה 4 — החזרת המינימום

`lookup_client` מחזיר שם וסיכום תיקים פעילים. **לא** סכומים, לא מספרי
תיק בבית משפט, לא מסמכים. מה שלא נשלח לא יכול להיאמר בטלפון למי שהתחזה
ללקוח. יש בדיקה שמאמתת בדיוק את זה.

### שכבה 5 — הצד שכנגד

מספר שתואם ל-`debtorPhone` בתיק פעיל מזוהה כצד שכנגד: לא נמסרים פרטים,
ולא נפתח ליד. פנייה כזו הופכת למשימה לעורך הדין. רישום החייב כליד מזהם
את צנרת המכירות ועלול להוביל לשליחת הודעה שיווקית למי שעומד מול הלקוח.

### הרשאות

| פעולה | תפקיד |
|---|---|
| צפייה בשיחות, תמלול, ציר זמן | כל חבר משרד |
| מצב בדיקה | כל חבר משרד |
| עריכת סוכן, prompt, כלים | בעל משרד |
| הגדרות טלפוניה, הקלטה, שמירה | בעל משרד |
| עצירת חירום | בעל משרד |

עריכה נעשית ישירות מהדפדפן דרך `aiUpdateChecked`, שמאמת שהשורה **באמת
נכתבה**. RLS מסנן שורות ולא זורק שגיאה — עדכון שנחסם חוזר כהצלחה עם אפס
שורות, ובלי הבדיקה המסך היה מציג "נשמר" בזמן ששום דבר לא השתנה.

### מה לא נמצא בשום מקום

* `service_role` key בדפדפן — לא.
* סודות ב-repository — לא. `.env` ו-`.env.local` ב-`.gitignore`.
* תוכן שיחה בלוגים — לא. הוא חי בתמלול, תחת מדיניות שמירה ובקרת גישה.
* מפתחות בלוגים — מסונן ב-`telemetry/logging.py`.

12 שיחות לשעה למספר (ניתן לשינוי), 30 שיחות בדיקה לשעה למשתמש. הבדיקה
נעשית **לפני** יצירת השיחה: שיחה שנוצרה כבר יצרה ליד ומשימה.

## 4. שרת הקול

`services/voice-gateway/` — Docker, שני שירותים ארוכי-חיים.

**אינו נפרס ל-Netlify ואינו רץ כ-Serverless.** שיחת טלפון היא חיבור
מתמשך של דקות עם זרם אודיו דו-כיווני, ו-Asterisk מחזיק רישום SIP חי.
סביבה שמתעוררת לבקשה ומתה אחריה לא יכולה לעשות אף אחד מהשניים.

```
services/voice-gateway/
    docker-compose.yml
    .env.example
    asterisk/
        pjsip.conf.template     תבנית — הסודות מוזרקים בזמן רינדור
        extensions.conf         dialplan מינימלי + חסימת לולאת ניתוב
        ari.conf
        http.conf               מאזין ל-127.0.0.1 בלבד
    orchestrator/
        app/
            main.py             FastAPI, heartbeat, בחירת ספקים
            config.py
            calls/              מחזור חיי שיחה
            audio/              AudioSocket
            stt/                STTProvider + faster-whisper
            llm/                LLMProvider + crm/ollama/vllm
            tts/                TTSProvider + mock/local
            telephony/          TelephonyProvider + Asterisk ARI
            tools/              שער הכלים (בקשות בלבד)
            crm/                לקוח חתום + תור מקומי
            security/           HMAC
            telemetry/          לוגים מובנים
        Dockerfile
        requirements.txt
    scripts/healthcheck.sh
    README.md
```

### Provider / Adapter

| שכבה | ממשק | מימושים |
|---|---|---|
| STT | `start_stream` / `push_audio` / `get_partial_transcript` / `get_final_transcript` | mock, faster-whisper |
| LLM | `generate` / `stream` / `tool_call` | **crm** (ברירת מחדל), mock, ollama, vllm |
| TTS | `synthesize` / `stream` | mock, local |
| Telephony | `answer_call` / `end_call` / `transfer_call` / `hold_call` | asterisk (ARI), mock |

**ברירת המחדל של LLM היא `crm`**, וזו לא עצלות: הסוכן, ה-prompt, רשימת
הכלים, ההרשאות וכללי הדחיפות חיים ב-CRM. הרצת מודל בשרת הקול הייתה יוצרת
מערכת שנייה עם prompt משלה שצריך לתחזק במקביל — ובעל המשרד לא היה רואה
במסך מה משתנה. `ollama`/`vllm` שמורים למקרה שבו השהיית סבב לענן הופכת את
השיחה ללא טבעית; גם אז **הכלים ממשיכים לעבור דרך שער הכלים של ה-CRM**.

### אין מנוע TTS עברי

לא נבחר, ולכן לא הומצא. `MockTTSProvider` מייצר שקט באורך שמתאים לטקסט
ומצהיר על עצמו — כך נבדקת כל זרימת האודיו (תזמון, framing, ניתוק, הפרעה)
בלי להעמיד פנים שיש קול. מנוע שהיה מדווח "תקין" ומחזיר שקט הוא הגרוע מכל:
הבדיקות עוברות, והלקוח הראשון לא שומע דבר.

### עמידות

תקלת רשת אינה מוחקת פנייה. בקשה שלא הגיעה ל-CRM נשמרת לדיסק
(`QUEUE_PATH`, כתיבה אטומית עם `os.replace`) ונשלחת שוב. האידמפוטנטיות
בצד ה-CRM היא מה שהופך את זה לבטוח — בלעדיה, תור עם retry היה מנגנון
לייצור פגישות כפולות.

`4xx` **לא** נכנס לתור: חתימה שגויה או שדה חסר לא יסתדרו בניסיון חוזר.

## 5. Asterisk

**Asterisk 22 LTS.** תפקידו: לקבל שיחה, לענות, לגשר, להעביר מדיה החוצה
ולקבל בחזרה, לנתק, להחזיק, ובעתיד להעביר. הוא **לא מכיר AI**.

### למה ARI ולא AGI/AMI

AGI מריץ תהליך לכל שיחה וחוסם את הערוץ. AMI הוא זרם אירועים בלי שליטה
טובה בערוצים. ARI נותן REST + WebSocket אחד ותומך ב-External Media —
כלומר להוציא אודיו מהשיחה אל תהליך אחר ולהחזיר. זה בדיוק מה שנדרש כדי
להכניס STT ו-TTS באמצע שיחה.

### שלוש מלכודות שכבר מטופלות בקבצים

**`network_mode: host`.** SIP ו-RTP מטמיעים כתובות IP *בתוך* גוף החבילה
(SDP). NAT של Docker מתרגם כותרות ולא תוכן. הסימפטום אינו "השיחה נכשלה"
אלא "השיחה מתחברת ואין קול בכיוון אחד" — התקלה שהכי קשה לאבחן בטלפוניה.

**`direct_media = no`.** עם `yes` הצדדים מדברים ישירות וה-AI לא שומע דבר.

**`Answer()` לפני `Stasis()`.** ערוץ שלא נענה אינו יכול לשאת מדיה.

### דילוג על ערוץ המדיה

ערוץ ה-External Media שאנחנו פותחים מייצר `StasisStart` בעצמו. בלי הסינון
ב-`parse_stasis_start` (`UnicastRTP`), כל שיחה הייתה נספרת פעמיים והמערכת
הייתה פותחת שיחה שנייה ב-CRM על ערוץ שהיא יצרה בעצמה.

### `check_calendar`

בודק קודם אם קיימת אינטגרציית יומן מחוברת (`getCalendarProvider` — Google
Calendar, שכבר קיים בפרויקט). אם כן — משתמש בה. אם לא — במנגנון הפגישות
הפנימי (`db.events`). **לא נוספה אינטגרציה חדשה.**

יומן חיצוני שנפל אינו סיבה לא להציע פגישה: נופלים לפנימי ומסמנים
`internal_fallback`.

### `create_appointment` — מניעת Double Booking

שתי בדיקות, כי אחת לא מספיקה:

1. מול ה-blob **הטרי** (`reload`), לא מול העותק שנטען בתחילת התור.
2. שוב **בתוך** ה-`mutate` של `saveOfficeDb` — ההזדמנות האחרונה לראות
   אירוע שנוצר בשנייה שחלפה.

בנוסף: סוף שבוע נדחה, תאריך שעבר נדחה, ומחוץ לשעות העבודה לא מוצע.

### `transfer_call` — למה הוא כבוי

```
available = false
unavailable_reason = "לא הוגדר HUMAN_TRANSFER_NUMBER. העברה למספר הציבורי
                      עלולה ליצור לולאת ניתוב — במקומה נוצרת משימת חזרה."
```

**התרחיש:** השיחה מופנית מ-055-274-5790 אל ה-AI. אם היעד להעברה הוא אותו
מספר, ההעברה מחזירה את השיחה לעצמה — ערוצים שנפתחים עד שהמערכת או הספק
קורסים, וחיוב על כל אחד.

ההגנה קיימת **בארבע שכבות**, כי פעולה שגורמת נזק מצטבר לא מקבלת הגנה
יחידה:

1. `agent_tools.available = false` — הכלי לא מוצע למודל כלל.
2. `tools.ts` — `samePhone(target, publicNumber)` → נחסם.
3. `extensions.conf` — `GotoIf` על היעד → ניתוק מסודר.
4. `config.py` — `transfer_target` מחזיר ריק כשהיעד זהה.

כשמגדירים מספר תקין, `settings.sync` מדליק את הכלי אוטומטית.

### מנוע הדחיפות

**לא Keyword matching בלבד.** שלושה מקורות, והחזק גובר:

1. **המודל** — מסווג בהקשר מלא. המקור העיקרי.
2. **מונחים** (ניתנים לעריכה במסך הסוכן) — **תקרה** ולא רצפה: מגיעים עד
   `high` לכל היותר. `critical` דורש הסכמת המודל, כי `critical` פירושו
   להעיר אדם.
3. **הקשר** — מועד קרוב, לקוח קיים, מתקשר חוזר.

בנוסף, בדיקת הקשר היפותטי: `"רציתי לשאול אם אתם מטפלים בעיקול"` אינו
חירום, `"קיבלתי עיקול"` כן. בלי ההבחנה הזו, אחרי שבוע של התראות שווא איש
לא מסתכל על סימון הדחיפות — ואז השיחה שבאמת דחופה נבלעת.

כל סיווג מגיע עם נימוק קריא. סיווג בלי נימוק אינו ניתן לערעור, ולכן אינו
ניתן לתיקון.

### מה קורה כשכלי נכשל

השיחה **ממשיכה**. המודל מקבל הודעת שגיאה קצרה, השורה נרשמת כ-`failed`,
והשיחה מסומנת `manual_followup_required=true`. בסיום נוצרת משימה. מתקשר
שנותק כי בדיקת יומן נפלה הוא התוצאה הגרועה ביותר האפשרית כאן.

## 10. חיבור SIP בהמשך

### לפני שמתחילים

1. בחר ספק SIP ישראלי. דרוש ממנו: מספר DID, פרטי רישום (host, username,
   password, realm), ותמיכה ב-`alaw`/`ulaw`.
2. הפנה את 055-274-5790 אל ה-DID, או העבר את המספר לספק.
3. שרת Linux עם IP קבוע. פתח: UDP 5060, UDP 10000-20000 (RTP).

### הפעלה

```bash
# 1. .env
SIP_HOST=sip.provider.co.il
SIP_USERNAME=<מהספק>
SIP_PASSWORD=<מהספק>
SIP_REALM=sip.provider.co.il
SIP_EXTERNAL_IP=<ה-IP הפומבי של השרת>
ARI_PASSWORD=$(openssl rand -hex 24)

# 2. עלייה
docker compose up -d

# 3. בדיקת רישום
docker compose exec asterisk asterisk -rx "pjsip show registrations"
#    → Registered

# 4. שיחה אמיתית
docker compose logs -f orchestrator
```

### ⚠ שלוש נקודות כשל נפוצות

**`SIP_EXTERNAL_IP` חסר.** השיחה מתחברת ואין קול בכיוון אחד. הגורם:
Asterisk מפרסם כתובת פנימית ב-SDP.

אבל אל תגדיר כך מלכתחילה. אם אין מספר נפרד — השאר ריק; משימת חזרה עדיפה.

```bash
supabase secrets list | grep VOICE_GATEWAY_SECRET

```

מרכז שיחות → הגדרות → ודא שהמספר נכון → שמור. ואז מצב מערכת: SIP 🟢.

כעורכת דין, מסירת מידע רגיש לפני אימות, פעולה שאינה ברשימת הכלים.

**במקרה ספק:** משימה לעורך הדין.

⚠ הסעיף האחרון נאכף **בקוד** ולא רק בטקסט. הסוכן יכול להפעיל רק את מה
שרשום ב-`agent_tools`, וה-gateway בודק מול ה-DB לפני כל ביצוע. מסמך,
מתקשר או מודל שהשתכנע אחרת אינם יכולים להרחיב את הרשימה.

## 14. כתיבה בטוחה ל-app_data

### הבעיה
כל ה-CRM הוא ערך `jsonb` יחיד. כתיבה היא read-modify-write על שורה
שלמה. אם הסוכן כותב בזמן שעורך הדין עורך כרטיס לקוח — אחד דורס את
השני, ואיש לא יודע שזה קרה.

### הפתרון: מוטציה ממוקדת, לא השמת מצב
`saveOfficeDb` כבר עשה את הדבר הנכון: קורא, מחיל את פונקציית המוטציה,
וכותב **רק אם** `updated_at` לא זז. אם זז — קורא מחדש ומחיל שוב, הפעם
על הנתונים החדשים.

```
זמן →
  [סוכן]  קורא blob(v1) ──────────────► מחיל "הוסף משימה" ──► כתיבה נדחית (v2≠v1)
  [משתמש]        └─► שומר עריכת לקוח ──► blob(v2)
  [סוכן]                                 קורא blob(v2) ──► מחיל שוב ──► blob(v3) ✓
```

**שני השינויים שורדים**, כי המוטציה אומרת *"הוסף את המשימה הזו"* ולא
*"כתוב את הבלוב הזה"*.

`applyOfficeCommand()` עוטף את זה בשלושה דברים שחסרו:
1. **אידמפוטנטיות** — הפקודה נרשמת לפני שהיא מוחלת.
2. **רשימה סגורה** — ה-AI לא מספק פונקציית `mutate`, הוא שולח שם מתוך
   רשימה של שבע פקודות. אין נתיב שבו קלט מהמודל הופך לקוד שרץ.
3. **תוצאה שמורה** — כדי להחזיר אותה שוב, ולענות בדיעבד על "מה ה-AI שינה".

**נבדק:** `שינוי של משתמש ושינוי של הסוכן — שניהם שורדים`.

### הפקודות
`create_lead` · `update_lead` · `create_task` · `create_note` ·
`create_appointment` · `create_callback` · `update_callback`

הרשימה זהה בקוד (`COMMAND_MUTATORS`) וב-DB (`check` על `command_type`),
ויש בדיקה שמאמתת שהן לא נפרדו.

## 15. אידמפוטנטיות

### המפתח
```
idempotency_key = call_id : command_type : tool_call_id
```

`tool_call_id` הוא מה שמבדיל בין שני מצבים שנראים זהים:

| | הקלט | tool_call_id | תוצאה |
|---|---|---|---|
| המודל חזר על עצמו / retry ברשת | זהה | **זהה** | התוצאה המקורית מוחזרת |
| המתקשר ביקש באמת שתי פגישות | זהה | **שונה** | שתי פגישות |

בלעדיו, מתקשר שביקש שתי פגישות זהות היה מקבל אחת. איתו, retry אחרי
timeout בטוח.

### שלוש שכבות
1. **בסכמה** — `unique(office_id, idempotency_key)` על `office_commands`,
   `unique(call_id, idempotency_key)` על `call_actions`.
2. **בקוד** — `applyOfficeCommand` בודק לפני שהוא מחיל.
3. **בנתונים** — כל מוטציה בודקת כפילות בעצמה (משימה זהה פתוחה, ליד
   מאותו מספר, מועד תפוס). זה תופס גם מקרים שהמפתח לא מכסה: שיחה שנייה
   מאותו מתקשר.

**נבדק:** אותו `tool_call_id` פעמיים → פעולה אחת · `tool_call_id` שונה →
שתי פעולות · retry על פגישה → אין כפילות.

## 16. בקשות חזרה — תכונת ליבה

**החלטת המוצר: אין העברה חיה לעורך הדין.** כל בקשה לדבר איתו הופכת
לבקשת חזרה, ולכן זו אינה תכונה משנית אלא מרכז הכובד של המוצר.

### המבנה
נשמר על המשימה הקיימת ב-blob (`db.tasks[].callback`), לא בטבלה מקבילה —
שתי רשימות משימות היו מפצלות את תשומת הלב של עורך הדין, וזה בדיוק מה
שגורם לאחת מהן להיזנח.

```js
callback: {
  sourceCallId, callerPhone, callerName,
  preferredCallbackTime, reason, urgency,
  status,              // waiting | contacted | no_answer | reschedule | completed | cancelled
  attemptCount, lastAttemptAt, completedAt, createdAt
}
```

### מחזור החיים
```
waiting ──┬─► contacted ──► completed
          ├─► no_answer  ──► (ניסיון נוסף)
          ├─► reschedule ──► waiting
          └─► cancelled
```

⚠ `attemptCount` עולה רק ב-`contacted` וב-`no_answer`. "נדחה למועד אחר"
אינו ניסיון חיוג, וספירתו הייתה מציגה לקוח כמי שניסו להשיגו חמש פעמים
כשלא ניסו כלל.

⚠ סגירת הבקשה (`completed`/`cancelled`) סוגרת גם את המשימה — אחרת היא
נשארת ברשימת המשימות הפתוחות לנצח.

### המסך
**מרכז שיחות → ממתינים לחזרה.** ממוין לפי דחיפות ואז ותק, עם סימון
ויזואלי לבקשה דחופה שממתינה מעל 4 שעות או לכל בקשה מעל יממה.

## 18. מכונת המצבים

```
ringing → answering → listening ⇄ transcribing → thinking
                          ▲                          │
                          │                          ▼
                          └── speaking ◄── waiting_for_tool
                                  │
                              completing → ended
```

`voice_state` נפרד מ-`status` בכוונה: `status` הוא מצב הטלפוניה
(מצלצל/פעילה/הסתיימה), `voice_state` הוא מה שהסוכנת עושה **בתוך** שיחה
פעילה. מיזוגם היה יוצר מצב שבו "בשיחה" לא מבחין בין הקשבה למתקשר לבין
המתנה לתשובת כלי — וזו בדיוק ההבחנה שדרושה כשמנסים להבין למה שיחה
נשמעה תקועה.

### האירועים
`LISTENING_STARTED` · `USER_SPEECH_STARTED` · `USER_SPEECH_ENDED` ·
`STT_STARTED` · `STT_COMPLETED` · `LLM_STARTED` · `LLM_FIRST_TOKEN` ·
`TOOL_STARTED` · `TOOL_COMPLETED` · `TTS_STARTED` · `TTS_FIRST_AUDIO` ·
`TTS_COMPLETED` · `BARGE_IN` · `SILENCE_TIMEOUT` · `AUDIO_LOST`

במסך השיחה הם מוסתרים כברירת מחדל מאחורי "הצג אירועים טכניים": שיחה בת
חמישה תורות מייצרת כשלושים אירועים, ובתוכם נבלעות שלוש השורות שבאמת
חשובות ("נוצרה משימה", "נקבעה פגישה").

## 19. Barge-In

### למה זה קריטי
אדם לא ממתין לצפצוף. מערכת שממשיכה להקריא משפט שכבר לא רלוונטי בזמן
שהמתקשר מדבר נשמעת כמו מענה קולי משנות התשעים — וזו בדיוק החוויה
שגורמת לאנשים לנתק.

### איך זה עובד
`AudioSocketServer.send` דוחף פריים כל 20ms **בקצב אמיתי**. זו לא
התחסכות: אילו כל המשפט היה נדחף לחוצץ של Asterisk בבת אחת, ביטול היה
בלתי אפשרי. השמעה היא לולאה שרצה, ולכן אפשר לצאת ממנה.

```
1. BargeInPolicy מזהה דיבור רצוף (≥100ms, אחרי 300ms חסד)
2. session.speaking = false          ← הלולאה ב-_speak יוצאת
3. transport.cancel_speech()         ← נתח נוכחי נעצר
4. transport.flush_output()          ← מה שבדרך מפסיק
5. turn.start_listening()            ← רק עכשיו חוזרים להקשיב
```

⚠ הסדר אינו שרירותי. היפוכו היה משאיר פריימים בדרך אחרי שכבר עברנו
להקשבה — כלומר ה-STT היה קולט את הקול של הסוכנת עצמה.

### חלון החסד
300ms בתחילת כל משפט. בלעדיו, הד של המילה האחרונה של המתקשר קוטע את
המשפט הראשון של הסוכנת לפני שהספיקה לומר מילה.

### כשלא נתמך
`supports_barge_in=false` → המדיניות **מכובה**. סימון הפרעה בלי יכולת
להשתיק היה יוצר מצב שבו הסוכנת ממשיכה לדבר ואנחנו מאזינים בו-זמנית.

## 22. Outbox מתמיד

### למה לא תור בזיכרון
`docker compose restart` באמצע היום מוחק אותו. מה שנמחק אינו "בקשת
רשת" — זו פנייה של לקוח שהמזכירה קיבלה ולא נרשמה, אחרי שהלקוח כבר קיבל
אישור בטלפון.

### SQLite
```sql
outbox(id, call_id, tool_call_id, idempotency_key, endpoint, action,
       payload, attempt_count, next_attempt_at, status, last_error)
```

| סטטוס | משמעות |
|---|---|
| `pending` | ממתין לשליחה |
| `sending` | בשליחה כרגע |
| `retrying` | נכשל, ממתין ל-backoff |
| `completed` | אושר ע"י ה-CRM |
| `dead_letter` | מיצה את הניסיונות |

**Backoff:** 1 → 2 → 5 → 10 → 30 → 60 שניות, ואז נשאר 60.

⚠ `4xx` שאינו retryable **לא** נכנס לתור: חתימה שגויה או שדה חסר לא
יסתדרו בניסיון חוזר. ה-CRM מסמן זאת ב-`retryable` שב-`VoiceError`, כדי
ששרת הקול לא ינחש.

⚠ פעולות ב-`sending` מריצה קודמת מוחזרות ל-`pending` בעלייה. אנחנו לא
יודעים אם ה-CRM קיבל אותן, והאידמפוטנטיות שם היא שתכריע. שליחה חוזרת
בטוחה; מחיקה אינה.

### Dead Letter
פעולה שמיצתה את הניסיונות מדווחת ל-CRM (`deadletter.report`), נשמרת
ב-`voice_dead_letters`, ומופיעה ב-**מצב מערכת → סנכרון פעולות** עם
פרטים ואפשרות לסמן כטופל. **היא לא נמחקת מקומית** — היא ראיה.

## 23. רמות זהות

| רמה | מתי | מה מותר |
|---|---|---|
| `unidentified` | ברירת מחדל | פרטי פנייה בלבד |
| `phone_match` | המספר מופיע ב-CRM | פנייה בשם הלקוח |
| `verified` | אימות נוסף (טרם מומש) | פרטי תיק |
| `rejected` | המספר תואם לצד שכנגד | אין מסירת מידע |

### ⚠ Caller ID אינו אימות זהות
טלפון אבוד, בן משפחה, או זיוף Caller ID מייצרים אותה התאמה בדיוק.
במדיניות `strict` (ברירת המחדל) `lookup_client` מחזיר את שם הלקוח —
פנייה בשם היא נוהג מקובל וסיכונה נמוך — אבל **לא** שמות תיקים ולא שלבי
הליך. מה שלא נשלח לא יכול להיאמר בטלפון למי שהשיג טלפון.

`identity_policy='phone_match_ok'` מקל על כך למי שמקבל את הסיכון
במודע. שכבת האימות עצמה (שאלת אימות, קוד SMS) לא מומשה — המבנה מוכן
לה: `identity_verified_at`, `identity_verification_method`.

## 24. גרסאות סוכן

כל שיחה שומרת snapshot בפתיחתה:

```
agent_config_version · prompt_hash · tools_policy_version
llm_provider/model · stt_provider/model · tts_provider/model
agent_snapshot (JSON: greeting, שעות פעילות, כללי הסלמה ודחיפות)
```

⚠ ה-snapshot נכתב ב-`insert` **ולעולם לא ב-`update`**. `prompt` שישונה
בצהריים לא יכול לשנות למפרע את מה ששיחה של הבוקר "התנהלה לפיו" — וזו
בדיוק השאלה שנשאלת כשמישהו מתלונן על משהו שהמזכירה אמרה. יש בדיקה
שמאמתת שאף `update` בקוד לא נוגע בשדות האלה.

⚠ שם הספק נלקח מה-**heartbeat** ולא מהגדרת הסוכן. הגדרה אומרת מה
רצינו; ה-heartbeat אומר מה באמת ענה למתקשר.

## 25. מנוע המוכנות לייצור

### ההבחנה שכל המנוע קיים בשבילה

```
healthy          = "השירות עצמו פועל"
production_ready = "אפשר לענות איתו לטלפון של לקוח"
```

`MockTTSProvider` **בריא לחלוטין**: עונה, מהיר, לא קורס. הוא גם מחזיר
שקט. מערכת שבודקת `healthy` בלבד הייתה צובעת אותו ירוק, בעל המשרד היה
מחבר מספר אמיתי, והלקוח הראשון לא היה שומע דבר.

`ProviderStatus.mock()` הוא הדרך היחידה לבנות מצב Mock, ו-
`production_ready` נעול שם על `False` — לא פרמטר, לא ברירת מחדל שאפשר
לדרוס.

### מה נבדק
CRM · אבטחה (סוד חתימה) · שרת טלפוניה · מרכזייה · SIP · ערוץ אודיו ·
STT · LLM · TTS · שער הכלים · סוכן · קו טלפון · Outbox · עצירת חירום

### הכשל הוא סגור
מידע חסר → **לא מוכן**. `never_connected` אינו "כנראה בסדר" — הוא הסימן
הבטוח ביותר שאין שרת קול.

### התוצאה
```json
{ "ready": false,
  "blocking_reasons": ["הקראה (TTS): mock במצב הדגמה — אינו מתאים לשיחות אמיתיות"],
  "warnings": ["סנכרון פעולות: 3 פעולות לא סונכרנו"] }
```

`blocking` חוסם הפעלה; `warnings` שווה לדעת ואינו מונע שיחה. רשימה אחת
ארוכה גורמת לאנשים להתעלם ממנה, ואז גם החוסמים נבלעים.

## 26. המתג של שיחות אמיתיות

`call_center_settings.live_calls_enabled` — **`false` כברירת מחדל**.

⚠ זה **לא** משתנה סביבה, ובכוונה. משתנה סביבה היה מאפשר להדליק את זה
ב-deploy בלי שאיש יבדוק אם יש בכלל מנוע הקראה.

### שני שערים, שניהם נדרשים
1. בדיקת המוכנות חייבת לעבור (`ready=true`). השרת מחזיר `409` אחרת.
2. ההפעלה היא של **בעל המשרד** מהמסך. גם מערכת מוכנה לחלוטין לא מדליקה
   את עצמה — קבלת שיחות בשם המשרד היא החלטה, לא תוצאה של תשתית
   שהתחברה.

### שלוש נקודות אכיפה
| היכן | מה קורה |
|---|---|
| `CallManager._on_start` | השיחה **לא נענית** כלל |
| `voice-gateway` → `call.start` | `423 LIVE_CALLS_DISABLED` |
| `agent_tools` | הכלים לא משתנים — הסוכן פשוט לא מופעל |

הראשונה חשובה במיוחד: אם נענה קודם ורק אז נגלה שהשיחה נדחית, המתקשר
כבר שמע צלצול ואז שקט.

כל שינוי במתג נרשם ב-`audit_logs` עם `severity: 'security'`.

## 28. חיבור ספק SIP — Provider Agnostic

**אין הנחה על ספק מסוים.** אין קוד ל-Twilio, ל-DIDWW, ל-019 או לאף
אחד אחר. מה שנדרש מספק כדי להשתלב:

| דרישה | חובה |
|---|---|
| SIP trunk עם רישום (username/password/realm) | ✓ |
| DID נכנס | ✓ |
| קודק `alaw` או `ulaw` | ✓ |
| תמיכה ב-`rtp_symmetric` / `force_rport` (NAT) | ✓ |
| Opus | רשות |

### ההפעלה
```bash
# 1. פרטי הספק
cd services/voice-gateway && cp .env.example .env
#    SIP_HOST / SIP_USERNAME / SIP_PASSWORD / SIP_REALM / SIP_EXTERNAL_IP
#    ARI_PASSWORD=$(openssl rand -hex 24)
#    VOICE_GATEWAY_SECRET=<זהה לזה שב-Supabase>

# 2. עלייה
docker compose up -d
docker compose exec asterisk asterisk -rx "pjsip show registrations"
#    → Registered

# 3. בדיקה
./scripts/healthcheck.sh

# 4. ב-CRM: מרכז שיחות → מצב מערכת → "בדיקת מוכנות מלאה"
# 5. כשהכול ירוק: "אפשר שיחות אמיתיות"
```

### שלוש נקודות כשל נפוצות
| סימפטום | סיבה |
|---|---|
| השיחה מתחברת, אין קול בכיוון אחד | `SIP_EXTERNAL_IP` חסר — Asterisk מפרסם כתובת פנימית ב-SDP |
| כל בקשה חוזרת 401 | `VOICE_GATEWAY_SECRET` שונה בין הצדדים |
| השיחה נענית ומיד מנותקת | `live_calls_enabled=false` — צפוי עד ההפעלה במסך |

## 29. אבחון — חלק ב׳

### "המערכת אומרת שהיא לא מוכנה, אבל הכול ירוק"
`healthy` ≠ `production_ready`. פתח **מצב מערכת → יכולות הספקים** —
העמודה "מוכן לייצור" היא הקובעת.

### "פעולה לא סונכרנה"
**מצב מערכת → סנכרון פעולות.** לכל שורה יש את הפעולה, מספר הניסיונות
והשגיאה. אחרי טיפול ידני — "סמן כטופל". אין מחיקה אוטומטית.

### "הסיכום לא הופק"
`post_call_status='failed'` — כפתור "נסה שוב" במסך השיחה, או המתנה
ל-`ai-cron` שמנקז pending ו-failed. הסיכום העובדתי הזמני נשאר בינתיים.

### "בקשת חזרה נעלמה"
היא לא נעלמת. `ממתינים לחזרה` מציג `waiting`/`no_answer`/`reschedule`;
`completed` ו-`cancelled` עוברים ל"טופלו" באותו מסך.

### "השיחה נשמעת איטית"
**ביצועים.** אם `P95` גבוה בהרבה מ-`P50`, הבעיה בזנב ולא בממוצע. הפירוק
לפי שלב אומר מי הצוואר: STT, מודל, כלים או הקראה.

### "הסוכנת מדברת מעל המתקשר"
`barge_in_enabled` בהגדרות, ו-`supports_barge_in` של התעבורה. שניהם
חייבים להיות true.
