## שלוש ההחלטות שמסבירות את כל השאר

### 1. ה-CRM הוא JSON יחיד, לא טבלאות
`app_data.data` — jsonb אחד לכל משרד. אין `clients`, אין `cases`.
לכן: `client_id`/`matter_id` בטבלאות ה-AI הם `text` (מזהי `uid()` base36), בלי FK.

### 2. הסוכן לעולם לא כותב ל-CRM
```
סוכן → הצעה ב-ai_approvals → אישור אנושי → החלה בדפדפן → saveDB()
```
זה פותר **שתי** בעיות בבת אחת: הדרישה המשפטית לאישור לפני פעולה רגישה,
והסכנה הטכנית של כתיבה מקבילה לאותה שורת blob (lost update).

### 3. סוכן = שורה, לא קוד
הוספת סוכן חדש = `INSERT` ל-`ai_agents` + `ai_agent_tools`. אין שינוי קוד.

## למידה מתמשכת — לומד מציע, אדם מאשר

המערכת אספה מהיום הראשון את כל התיקונים שלך — מה ערכת לפני שאישרת, למה דחית,
מה ביקשת לשנות — ולא למדה מהם דבר. `ai-learn` סוגר את הלולאה: הוא קורא את
הסיגנלים האלה, מזהה גם עבודה שחוזרת על עצמה **ללא** תיקונים, ומזקק מהם לקחים.
כל לקח נשמר כ**הצעה** עם הראיות שהובילו אליה, ואינו משנה דבר בהתנהגות הסוכן עד
שבעל המשרד מאמץ אותו במסך "למידה" — ואז הוא נכנס ל-`ai_memories` ומשם ל-prompt
של אותו סוכן בכל הרצה הבאה. כל אימוץ ניתן לביטול, וביטול מוחק את הלקח.
במערכת שמפיקה מסמכים משפטיים, סוכן שמשנה את התנהגותו לבד הוא סוכן שאי אפשר
להסביר בדיעבד למה עשה מה שעשה.

## מה נבנה

| רכיב | פירוט |
|---|---|
| Gateway | `ai-gateway` — אימות, הרשאות, ניתוב כוונה, idempotency, תקציב |
| תור | `ai_jobs` + `claim_ai_job()` עם `FOR UPDATE SKIP LOCKED` |
| Worker | `ai-worker` — orchestration, לולאת tool-use, תיעוד מלא |
| מתזמן | `ai-cron` — ניקוז, התאוששות, מנוע אוטומציות, סבב למידה |
| לומד | `ai-learn` — סיגנלים → זיקוק → תובנות מוצעות. לא משנה שום הגדרה לבד |
| כלים | 37, ברמות סיכון none→critical |
| סוכנים | 13 |
| אישורים | 12 פעולות בחסימה קשיחה |
| UI | פאנל אחד, 13 טאבים, בעברית מלאה RTL |
| אינטגרציות | Gmail · יומן · WhatsApp · טלפוניה (interface + mock) |
| בדיקות | 75 עוברות |
